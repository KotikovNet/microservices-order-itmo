# Микросервисная система управления заказами — проектный дизайн

## Назначение

Создать понятное локально запускаемое приложение управления заказами из трёх независимых Spring Boot сервисов. Каждый
сервис владеет своими данными и предоставляет REST API; заказ проверяет пользователя по HTTP, сохраняется в своей БД,
затем запрашивает у Notification Service фиксацию имитации отправки уведомления.

## Цели

- Реализовать перечисленные в ТЗ операции CRUD и поиск по пользователю.
- Проверять пользователя до сохранения заказа и не обращаться к его БД напрямую.
- Хранить пользователей, заказы и уведомления в трёх PostgreSQL.
- Поддержать валидацию, единый формат безопасных ошибок, настройку URL/БД из окружения, Docker Compose и понятную
  документацию.
- Собрать и по возможности практически запустить систему; не заявлять о непроверенном.

## Не входит

- Kubernetes, очереди, Spring Cloud, общая библиотека DTO между сервисами, настоящая отправка email, аутентификация и
  авторизация.
- Любые тестовые классы/директории и зависимости тестирования (запрещены исходным ТЗ).

## Ограничения

- Java 21, Spring Boot 3.x, Spring Web, Spring Data JPA, PostgreSQL, Maven multi-module, Docker/Compose.
- HTTP REST — единственный канал межсервисного взаимодействия; синхронный Spring `RestClient` с конечными таймаутами.
- Отдельное приложение, схема и учётные данные БД для каждого сервиса; DTO объявляются локально в вызывающем сервисе.
- Конструкторная инъекция, Jakarta Validation, `@RestControllerAdvice`, без утечки stack trace и внутренних деталей.
- Не добавлять тестовую инфраструктуру; практическая проверка сборки/Compose/API разрешена и требуется ТЗ.

## Рассмотренные подходы

1. **Прямая синхронная цепочка REST (выбран).** Order Service вызывает User Service, сохраняет заказ, затем вызывает
   Notification Service. Минимум компонентов, совпадает с заданным сценарием и делает ошибки зависимостей наблюдаемыми.
2. **Синхронный вызов с фоновым повтором уведомления.** Надёжнее при временном сбое уведомлений, но потребует хранения
   состояния/повторов и дополнительной логики, которых ТЗ не просит.
3. **Очередь или распределённая транзакция.** Исключены ограничениями и неоправданно усложнят учебный локальный проект.

## Поведение и проектные решения

- REST сущности возвращаются DTO, чтобы не раскрывать JPA-модель. Создание возвращает `201 Created`, чтение/обновление —
  `200 OK`, удаление — `204 No Content`; отсутствующий ресурс — `404`, неверный ввод или конфликт email — `400`/`409`,
  недоступная зависимость — `503`.
- Email проверяется на формат и уникальность с ограничением в БД. Сумма заказа должна быть положительной; строки с
  именем, описанием, email и адресом получателя не должны быть пустыми. Статус заказа ограничен `NEW`, `PROCESSING`,
  `COMPLETED`, `CANCELLED`; начальный статус — `NEW`.
- Недоступность User Service приводит к `503`, заказ не сохраняется. Если пользователя нет — `404`, заказ не
  сохраняется. Если Notification Service не отвечает после успешного сохранения, Order Service сообщает `503` с
  нейтральным кодом/сообщением, не выдавая внутренних подробностей; уже сохранённый заказ остаётся созданным. Клиент
  может проверить заказ через GET перед повтором запроса.
- Уведомление содержит userId/orderId/email/сообщение, статус `SENT`, создано сейчас; сервис записывает факт имитации
  отправки в лог. Order Service получает email пользователя по DTO из проверки User Service.
- Ошибки в каждом сервисе имеют единый JSON вид с timestamp, status, code и message. Ошибки БД переводятся в безопасный
  `500`; детали остаются только в серверном логе.
- Сервисы и БД имеют healthcheck. Compose ждёт здоровые БД перед запуском приложений; порядок запуска сервисов не
  является готовностью бизнес-эндпоинта, поэтому сетевые ошибки всё равно обрабатываются.
- Hibernate `ddl-auto=update` предназначен только для локальной разработки. Секреты задаются env-переменными,
  `.env.example` содержит только демонстрационные значения.

## Архитектура и структура

Корневой Maven parent агрегирует `user-service`, `order-service`, `notification-service`. Каждый модуль содержит
собственное Spring Boot приложение, `controller`, `service`, `repository`, `entity`, `dto`, `exception`, `config`,
`application.yml` и Dockerfile. Корень содержит `docker-compose.yml`, `.env.example` и README с API, curl-примерами,
запуском и полным сценарием заказа.

Внешняя последовательность: клиент → Order Service → User Service (проверка и email) → локальная БД заказа →
Notification Service → локальная БД уведомлений. Каждый сервис обращается только к собственной БД.

## Что остаётся исполнителю

Подобрать совместимые версии Spring Boot 3.x и Maven плагинов, конкретные лимиты строк, порты и имена env переменных;
держать конфигурацию компактной. После согласования дизайна составить пошаговый план, реализовать сервисы по очереди,
затем проверить компиляцию, compose-конфигурацию, Docker и полный HTTP-сценарий настолько, насколько позволяет среда.
